# Design Notes

Running log of game-design and technical decisions made during development. Updated as the project progresses through the 8-phase roadmap (Foundations → Idle combat loop → Loot & relics → Companions & spells → HUB & meta-progression → Content scale-up → AI asset pipeline → Polish).

## Phase 1 — Foundations

**Scope:** project scaffold, folder structure, a typed data system proven on one content type (monsters), and a minimal `CombatEngine` (hero vs. one monster, flat damage, live HP). No loot, relics, companions, spells, HUB, persistence, or real art yet — those are later phases.

### Decisions

- **Phaser 4 instead of Phaser 3.** Phaser 4 has graduated to a stable release (4.2.1 on npm, `latest` tag) since this project's original brief assumed 3.x was the safer choice. Checked the bundled migration guide (`node_modules/phaser/changelog/v4/4.0/MIGRATION-GUIDE.md`) — none of the breaking changes (new WebGL render-node renderer, Filters replacing FX/Masks, `Point` → `Vector2`, etc.) affect the basic `Scene`/`Graphics`/`Text` API this project uses, so there's no cost to taking the current stable major instead of pinning to the previous one.
- **Content authored as typed TS object literals, not JSON, for now.** A generic `Registry<T extends { id: string }>` is the scalable piece; swapping the authoring format to JSON + schema validation (e.g. zod) later is a mechanical change to the loader, not the content shape. Deferred until content volume in Phase 6 makes hand-written `.ts` files unwieldy.
- **Seeded RNG (`Rng`, mulberry32-style) wired into `CombatEngine` from day one**, even though Phase 1's damage formula is flat and doesn't consume randomness yet. This locks in determinism/testability before crit rolls, drop rates, and relic proc chances arrive in later phases — retrofitting seeded RNG after the fact tends to be painful.
- **`CombatEngine` is fully renderer-independent.** It has no Phaser or React imports; it exposes `getState()` and `tick(dtMs): CombatEvent[]`. `CombatScene` (Phaser) is a pure subscriber — it reads state and reacts to events, but never mutates HP or decides win/lose itself. This is the seam that keeps combat logic unit-testable and the rendering layer swappable.
- **Phaser mounts inside React via a `useRef`-held `Phaser.Game` instance**, created in a `useEffect` guarded against React StrictMode's double-invoke (`if (gameRef.current) return`), destroyed with `game.destroy(true)` on unmount. The `Phaser.Game` object itself is never put in React or Zustand state — it's imperative and non-serializable.
- **`noUncheckedIndexedAccess: true`** added to `tsconfig.app.json` (on top of `strict: true`, added explicitly since the current Vite template doesn't set it by default). Matters immediately for the `Registry` map lookups and will matter more as relic/spell/item registries multiply in later phases.
- **Placeholder-first art.** Hero and monster are drawn as colored `Phaser.GameObjects.Rectangle` shapes with text-labeled HP bars — no sprites yet. `/src/assets` isn't created until a phase actually needs a placeholder image asset.

## Phase 2 — Idle combat loop

**Scope:** an infinite wave-based run (not just a single fight), hero XP/leveling, mini-boss/boss cadence with escalating difficulty, player-selectable simulation speed (x1/x2/x4), and enough HUD to see it all. Still placeholder rectangles — real art is Phase 7.

### Decisions

- **`WaveManager` sequences `CombatEngine` instances rather than extending `CombatEngine` itself.** `CombatEngine` stays a clean, single-fight primitive (unchanged from Phase 1); `WaveManager` owns the run-level concerns — spawning the next monster, carrying the hero's HP/stats forward, awarding XP, rolling level-ups, and picking monster tier/difficulty per wave. Same separation-of-concerns principle as Phase 1: pure, renderer-independent, unit-tested (`WaveManager.test.ts`, `waveScaling.test.ts`, `heroProgression.test.ts`).
- **Wave cadence, not hero level, drives mini-boss/boss spawns.** Every 5th wave is a mini-boss, every 10th (a multiple of 5) is a boss (`MINIBOSS_WAVE_INTERVAL` / `BOSS_WAVE_INTERVAL` in `waveScaling.ts`). Hero leveling is a separate, XP-driven axis — matches the brief's distinction between "vagues" (wave loop) and "niveaux" (hero progression).
- **Monster stats scale per-wave via a multiplier applied on top of each monster's base definition** (`scaledMonsterStats`), rather than baking difficulty into the content files. Keeps `MonsterDefinition` entries reusable at any wave and the difficulty curve centrally tunable in one function.
- **HP carries over between waves, with a partial (30%) heal of missing HP on each wave clear (`WAVE_CLEAR_HEAL_FRACTION`), on top of any maxHp gained from leveling.** A full heal every wave would remove all stakes from an idle loop that's supposed to feel like a real run; zero recovery turned out to be too punishing in practice — an early playtest died on wave 3 to ordinary monsters before any real "power spike" moment landed. 30% recovery plus a softened wave-scaling curve (down from +15%/+10% per wave to +10%/+6%) produced a much better arc in testing: routine waves feel survivable, and the mini-boss at wave 5 reads as a real difficulty wall rather than an arbitrary death. Full balance tuning is still explicitly deferred to Phase 8 — this is just enough to make the loop feel intentional rather than broken.
- **Speed control (x1/x2/x4) scales simulation `dt`, not engine internals.** `CombatScene` multiplies Phaser's frame `delta` by the store's `speed` value before calling `waveManager.tick()`. Neither `CombatEngine` nor `WaveManager` has any concept of "speed" — it's purely a rendering-loop concern, keeping the simulation logic simpler and more testable.
- **First real use of Zustand: a `runStore` bridging `CombatScene` (Phaser) and the React HUD.** The scene is the source of truth (owns the `WaveManager`) and pushes a plain-data snapshot into the store every tick; React only reads it and writes back UI intents (`setSpeed`, `requestRestart`). This is the "run state" store from the target architecture — the separate "meta state" store still doesn't exist until Phase 5.
- **Restart is a token bump, not a scene reload.** `requestRestart()` increments `restartToken` in the store; `CombatScene.update()` notices the token changed and rebuilds a fresh `WaveManager` and unit views in place. Keeps the Phaser `Game` instance alive across runs instead of tearing down and remounting it.
- **Content added: 5 normal monsters (goblin, slime, wolf, skeleton, cave bat), 1 mini-boss (Orc Chieftain), 1 boss (Ancient Wyrm)** — enough variety to make wave-to-wave monster selection (random pick within tier) visible, without front-loading all 60-80 V1 relics/monsters here; bulk content growth is Phase 6.
- **Level-up and mini-boss/boss tier are the only new visual treatments added this phase** (a floating "LEVEL UP!" toast, and size/color differentiation per `MonsterTier` in `CombatScene`). Gacha-premium chrome (borders, glow, rarity-driven animation) is explicitly Phase 8 polish, not introduced early.

## Phase 3 — Loot and relics

**Scope:** the Balatro-style relic system (the brief's "cœur du jeu"), equipment with rarity, and a loot-choice popup between waves. 18 relics across 6 tag families, 6 equipment archetypes, rarity-colored UI. Companions/spells are still Phase 4; the 60-80 relic target and gacha-premium chrome are Phase 6/8.

### Decisions

- **Relic effects are a declarative modifier vocabulary, not per-relic scripted code.** `RelicModifier` is a small discriminated union (`damageMultiplier`, `critChance`, `burnChance`, `lifestealPercent`, `executeThreshold`, `reflectDamagePercent`, `attackSpeedMultiplier`, `maxHpBonusPercent`, `goldMultiplier`, `xpMultiplier`, `regenPerWave`, etc.). `aggregateModifiers()` sums every owned relic's (and equipped item's) modifiers into one `AggregatedModifiers` object per wave. This keeps the system testable and scalable to 60-80 relics without a scripting engine, while still producing real multiplicative synergy: independent modifiers act at different stages of the same damage pipeline (base damage → crit multiply → burn add-on → lifesteal off the final total), so a crit-chance relic and a crit-damage relic compound in practice even though each is "just" additive within its own kind.
- **One relic (Phoenix Heart, mythic) is deliberately bespoke, not declarative.** A one-time revive-at-50%-HP can't be expressed as a stat modifier, so it's hand-coded in `WaveManager.tryPhoenixRevive()`, gated by a `special: 'phoenixRevive'` marker on its definition. This is the pattern for future "rule-transformation" relics (per the brief's requirement that legendary/mythic items should "change the rules," not just add stats) — declarative modifiers for the common case, bespoke engine code for the rare capstone effect.
- **Only the hero's attacks consult relic/equipment modifiers; monsters never do.** `CombatEngine.resolveAttack` branches on `attacker.id === heroId`. With `NEUTRAL_MODIFIERS` (the default), the new crit/burn/lifesteal/execute/reflect pipeline is a byte-for-byte no-op — verified by keeping every Phase 1/2 `CombatEngine` test passing unchanged after the refactor, plus new tests that pin each modifier's behavior in isolation (e.g. `critChanceSum: 1` always crits, `reflectDamagePercentSum` punishes a monster that attacks a reflect-carrying hero).
- **Equipment reuses the exact same modifier vocabulary as relics, scaled by rarity at drop time**, rather than a separate affix/roll system. Each `EquipmentDefinition` carries one `RelicModifier` at its common-rarity magnitude; `RARITY_POWER_MULTIPLIER` scales it when the item drops. Equipment differs from relics only in *how it's held* — one slot (`weapon`/`armor`/`accessory`), replacing whatever was there — not in how its effect is computed. True multi-affix rolls with ranges are a plausible Phase 6+ enhancement, not needed to validate the mechanic now.
- **Loot is offered after every wave clear, pausing the sim.** The brief's "2-4 choices" is fixed at exactly 3 for now (pacing/frequency is easy to retune later — a documented open question, not a commitment). `WaveManager` doesn't auto-advance after a win anymore: it sets `isChoosingLoot` and waits for `chooseLoot(index)`. `generateLootOptions()` weights relic/equipment/gold categories, rolls rarity via the drop-weight table, and defensively falls back (lower rarity → any rarity → gold) so a nearly-exhausted relic pool never crashes loot generation — relevant now with only 18 relics, less so once Phase 6 adds far more.
- **Hero HP/maxHp/attack-interval growth (leveling, gear, relics) is now computed fresh every wave inside `buildWaveEngine`, in one place.** Previously (Phase 2) the level-up HP delta was carried over as a separate calculation in `handleWaveCleared`; now that maxHp can also change from a relic or equipped item picked in the very loot popup that just closed, unifying "compute current max stats, then heal a fraction of whatever's missing" into a single wave-clear heal (`WAVE_CLEAR_HEAL_FRACTION`, boosted by any `regenPerWave` relics) is simpler and treats every maxHp source consistently.
- **Gold has no spend sink yet.** It accrues only when a player picks a "gold" loot option (no passive per-wave drip — gold is one of the three mutually-exclusive loot choices, matching the brief's "Or / ressources de forge" as a loot-pool category, not a separate economy). The forge/shop that spends it is Phase 5.

## Phase 4 — Companions and spells

**Scope:** recruitable companions (tank/dps/healer/support/summoner) fighting alongside the hero, and active/passive spells. 6 companions, 8 spells (4 active, 4 passive). Loot now has 5 categories (relic/equipment/companion/spell/gold). Full relic-companion cross-synergy and richer spell effects are left for later content passes.

### Decisions

- **Combat generalizes from strict 1v1 to hero + optional allies + optional spell casters, all as independently-timed actors in one tick loop.** `CombatEngine` gained `AllyUnit[]` and `SpellCaster[]` parameters (both defaulting to empty), scheduled alongside the hero/monster by `nextAttackAt`/`nextCastAt`. With no allies/spells (the default), this is provably the same engine as Phase 1-3 — every prior `CombatEngine` test still passes unchanged.
- **The monster's target is a taunt-weighted roll across the hero and any living allies**, not always the hero. Tanks get weight 4 vs. everyone else's 1, so they reliably (not absolutely) draw more attacks — verified statistically over 100 seeds in a test rather than asserting a single deterministic outcome, since the targeting is intentionally randomized.
- **A companion dying never ends combat; only the hero or the monster dying does.** `combatEnd`'s `winnerId` always resolves to the hero's or monster's id, never a companion's or a spell's, even when a companion's attack or a spell lands the killing blow — the run is always "the hero's run."
- **Companion behavior is dispatched by role, not by scripted per-companion code**: tank/dps/summoner attack the monster on their own timer (summoner adds a double-strike chance), healer restores the party's lowest-HP member instead of attacking, and support **never takes a turn at all** — its effect is a passive aura folded directly into `heroModifiers` via the same `aggregateModifiers()` pipeline used for relics/equipment/passive spells. This reuses Phase 3's infrastructure instead of inventing a second effect system.
- **Companions carry HP across waves like the hero (same wave-clear heal fraction), but a companion that reaches 0 hp stays permanently fallen for the rest of the run.** This is a deliberate stakes decision distinct from the hero (who can lean on Phoenix Heart, healers, etc. but never truly "loses" a slot) — losing a companion is a real, run-long cost, not a wave-scoped inconvenience. Verified in `WaveManager.test.ts` by injecting a 0-hp companion directly into state and confirming it's excluded from the next wave's fielded allies.
- **Active spells are structurally almost identical to companions in the engine** (their own cooldown timer, resolved in the same tick loop) but conceptually distinct in content (`SpellDefinition` is a discriminated union on `kind: 'active' | 'passive'`, separate from `CompanionDefinition`) and in loot rules (capped at 2 *active* slots; passive spells stack unlimited like relics, sharing `aggregateModifiers()` again). Active spell effects are deliberately a small closed set for now (`damage` / `heal` / `burn`) rather than a scripting system — enough to prove the mechanic, matching how Phase 3 kept relics declarative rather than scripted.
- **Relic/equipment modifiers still only ever apply to the hero's own attacks — companions fight with their own flat, unmodified stats.** Full "relics synergize with companions too" cross-play (e.g., a fire relic making a companion's hits also burn) is real depth the brief gestures at, but is scoped out of Phase 4 to keep this phase's surface area shippable; a natural target for the Phase 6 content pass once the base mechanic (this phase) is proven out.
- **Support aura eligibility is computed once at wave-build time, not re-evaluated mid-fight.** If a support companion dies mid-wave, the party keeps its aura bonus for the remainder of that wave (the `CombatEngine` instance already has `heroModifiers` baked in at construction) — it drops out starting the *next* wave once `buildAlliesAndSpells` re-aggregates. Fully live aura withdrawal would require swapping `heroModifiers` on a running engine mid-tick, adding real complexity for a marginal realism gain at this stage.

## Phase 5 — HUB and meta-progression

**Scope:** the HUB (Camp) the player returns to after every run, with a talent tree, forge, companion codex, and grimoire, backed by real local persistence (`idb-keyval`) — the first "meta state" store, kept strictly separate from `runStore`. The app now boots into the HUB rather than auto-starting combat, matching the brief's actual intended flow.

### Decisions

- **Gold's promised Phase 3 "sink" arrives here: run gold converts 1:1 into a permanent currency ("essence") the instant a run ends.** No separate meta-currency grind was introduced — the run currency simply *becomes* the meta currency at the `runOver` event, converted exactly once (`CombatScene` calls `depositCurrency` inside its `runOver` event handler, which only ever fires once per run). This directly serves pillar #4 ("even a failed run makes permanent progress") without adding a second economy to track.
- **`WaveManager` never touches Zustand or `idb-keyval` — it stays exactly as framework-free and unit-testable as every prior phase.** Meta-progression bonuses (talent ranks, forge level, companion upgrade ranks, loot luck) are resolved into plain data (`MetaBonuses`) by pure functions in `src/engine/talents.ts` and handed to `WaveManager`'s constructor as a plain parameter, the same pattern already used for `heroDef`. `CombatScene` (the impure glue layer that already reads `useRunStore`) is the only place that reads `useMetaStore`, computing `MetaBonuses` once per run start. This is the same "engine takes data in, UI layer bridges to stores" boundary from Phase 1, now proven across a second store.
- **Talents reuse the `RelicModifier` vocabulary a fourth time** (relics → equipment → passive spells → now talents), plus one new effect kind (`lootLuck`) for the one talent that can't be expressed as a combat stat — it shifts `pickRarity`'s odds away from common toward rare+ tiers instead. Extending `pickRarity` with an optional `luckBonus` parameter (default 0) kept every existing loot test passing unchanged.
- **Companion meta-upgrades boost attack/healing output only, never HP.** An early version scaled `maxHp` too, which broke the wave-clear heal math: HP carry-over/heal-fraction bookkeeping (`pendingCompanionHp` vs. a companion's base `maxHp`) only works if `maxHp` is a stable, single-scale reference across waves. Rather than thread a second "upgraded max" through that whole pipeline, upgrades stay output-only — simpler, and "your companions hit harder as you invest in them" is just as satisfying as a HP bump.
- **The Forge is a single global level, not a per-item upgrade/fusion system.** Equipment has no persistent identity across runs (it's regenerated fresh from loot each run, as decided in Phase 3), so "upgrading gear you found" doesn't map cleanly onto the current model yet. Forge level instead permanently scales the power of *any* equipment rolled in future runs (+1%/level, capped at 20). True per-item persistence, fusion, and sacrifice — the richer version of "forge" the brief describes — needs equipment to have a persistent identity first, a natural Phase 6 follow-up once there's enough equipment content to justify it.
- **The Grimoire/Codex unlocks entries on acquisition, not on mere sighting in a loot popup.** "Discovered" means the player actually picked a relic/spell/equipment/companion (via the `lootChosen` event) or fought a monster (via `waveStarted`) — offering-but-not-picking doesn't unlock the entry. Simpler to hook (both are events already flowing through `CombatScene`) and arguably a more satisfying "collection" framing than unlocking on sight.
- **`idb-keyval` persistence is a plain module-level hydrate-then-subscribe pattern, not a Zustand persist middleware** (none is installed). `metaStore.ts` reads the saved blob once on module load, applies it, then subscribes to all future state changes and re-saves the persisted slice (currency/talents/forge/upgrades/discoveries — explicitly not the transient `screen` field, which always resets to `'hub'` on load, and not a run in progress, which isn't persisted at all). Verified end-to-end with Playwright: earned essence, purchased a talent rank, reloaded the page, and confirmed both survived.
- **The old `restartToken` mechanism (Phase 2) was removed, not left dead.** Now that `<PhaserGame>` only mounts while `screen === 'run'`, entering the HUB naturally unmounts the Phaser `Game` instance and starting a new run remounts it fresh — `CombatScene.create()` already calls `startNewRun()` on every mount, so the token-bump plumbing that used to force an in-place reset had no remaining purpose and was deleted along with its now-unused `requestRestart` action.

## Phase 6 — Content scale-up

**Scope:** hit the V1 relic target (60-80) and add more monster/boss/equipment variety, purely by adding data through the existing registries — no engine or UI changes at all this phase, which is exactly the point ("s'appuyant sur le système de données pour scaler vite"). Companions/spells weren't part of this phase's brief and were left untouched.

### Decisions

- **New relics/monsters/equipment are grouped into one file per family/batch (`firePack.ts`, `pack2.ts`, ...) instead of one file per entry.** The established convention since Phase 3 was one file per relic; for bulk scale-up that convention would mean 42 near-identical tiny files for the new relics alone. Phase 5's talent branches already set the "grouped by category" precedent for this kind of volume content — Phase 6 follows it explicitly. The registries (`relics/index.ts`, `monsters/index.ts`, `equipment/index.ts`) spread these arrays in alongside the existing individually-filed entries, so both patterns coexist without any migration.
- **Landed at exactly 60 relics** (18 existing + 42 new, verified via `allRelics.length`), the low end of the brief's 60-80 target rather than the high end — the existing 6 tag families (fire/crit/blood/economy/speed/vitality) already had good coverage from Phase 3; the goal here was hitting the volume bar with sensible variety per family (~7 new each) rather than padding further for its own sake. Distributed roughly along the existing rarity curve: 18 common, 12 rare, 8 epic, 2 legendary, 2 mythic added.
- **No new `RelicModifierKind` values were introduced.** All 42 new relics, and all 6 new equipment pieces, reuse the existing 15-kind modifier vocabulary from Phase 3 — new *combinations* and magnitudes (e.g. `Hemorrhage`: lifesteal + crit chance; `Ashen Core`: crit-triggered bonus burn) create the variety, not new mechanics. Keeps this phase pure content with zero engine risk.
- **Monsters roughly doubled (7 → 16): 10 normal, 3 miniboss, 3 boss** (5 new normal, 2 new miniboss, 2 new boss). Since `WaveManager` already picks randomly within a tier's pool, this alone makes miniboss/boss waves feel less repetitive (previously always Orc Chieftain / Ancient Wyrm; now one of three) without touching `buildWaveEngine` at all.
- **Equipment doubled (6 → 12, 2 new per slot)**, still one modifier each — the "true multi-affix rolls" enhancement noted as a Phase 6+ possibility in the Phase 3 notes was deliberately not pursued here either; this phase is breadth (more templates), not new depth per item.
- **Verification for this phase leaned on the automated suite (typecheck/vitest/lint/build) plus a direct content-count check rather than a full Playwright visual pass** — appropriate for a phase that added zero new mechanics or UI surface; the loot/combat/HUB systems exercising this content were already visually verified in Phases 3-5.

## Phase 7 — AI asset pipeline

**Scope:** a real, working `scripts/asset-gen/generate.mjs` pipeline (AI Horde primary, Pollinations.ai fallback, per the brief) plus a priority manifest and an actual generated batch, integrated with a graceful-failure pattern so the game never depends on any of it. Session budget was tight for this pass, so scope leaned deliberately conservative — see decisions below.

### Decisions

- **The actual generation run used Pollinations only (`--skip-horde`), not AI Horde, despite both being implemented.** AI Horde is a shared community queue with unpredictable wait times; under a hard token/time budget, a quick connectivity check confirmed Pollinations responds in ~2s, so the real batch used it exclusively for speed and predictability. `generateViaAiHorde()` is fully implemented (submit + poll `generate/status` + fetch) and is the default path (`--skip-horde` opts out) for future runs with more time to spare.
- **Found and fixed a real bug during the actual run**: the pacing delay was only applied after *successful* Pollinations calls, so a string of failures fired back-to-back and instantly tripped the anonymous rate limit (HTTP 429) for the entire first batch (13/13 failed). Fixed by (a) always pacing between requests regardless of outcome, and (b) adding retry-with-backoff specifically for 429s inside `generateViaPollinations`. This is exactly the kind of thing "génère you génère en masse puis relance les échecs" resumability was designed for — the failure log made re-running only the misses trivial.
- **Result: 12 of 13 priority assets generated** (hero knight, 7 monsters including one boss, all 5 rarity icons; only `slime` still fails after two attempts). Not chased further to conserve budget — `node scripts/asset-gen/generate.mjs --only=slime` will pick it up whenever it's next run, resumable by design.
- **Integration is deliberately narrow and low-risk: plain React `<img>` tags with an `onError` handler that hides the element, never touching Phaser.** `RarityIcon` (loot cards) and `GeneratedPortrait` (HUB header, Bestiary thumbnails) are the only consumers. The working, tested rectangle-based `CombatScene` rendering was **not** touched — swapping it for real sprites would need a materially riskier refactor (Rectangle vs. Image have different APIs for resize/tint used throughout `updateUnitView`/`resizeMonsterView`), which isn't worth risking under a tight budget when the combat visuals already work correctly. This is squarely inside the brief's own "never block gameplay on asset generation" principle — placeholders remain the rendering path for combat; generated art augments HUB/UI screens where it's free to add or fail silently.

## Phase 8 — Polish (light pass)

**Scope:** given remaining budget, a targeted pass rather than exhaustive polish — the highest-value cheap wins, plus an honest accounting of what's left for a future pass.

### Done this phase
- **Rarity-driven animation on legendary/mythic loot cards**: a pulsing glow for legendary, an animated rainbow hue-rotation border for mythic — directly matching the brief's "rouge/arc-en-ciel animé=Mythique" call-out, CSS-only.
- **A `README.md` that actually describes the project** (was still the default Vite template through Phases 1-6).
- **One explicit multi-modifier "combo" test** (`CombatEngine.test.ts`) that resolves `flatDamageBonus` + `damageMultiplier` + guaranteed crit + `critDamageMultiplier` together and asserts the exact compounded number — a concrete, checked example of the synergy math the whole relic system is built around, rather than only unit-testing each modifier in isolation.

### Explicitly not done (honest scope-out, not an oversight)
- **No deep balance/difficulty pass.** The wave-scaling curve was tuned once from real playtesting in Phase 2 (see that section) and never revisited at full 60-relic content scale. It's a reasonable baseline, not a tuned one — a real balance pass needs many playtests across relic/companion/spell combinations, which wasn't affordable here.
- **No further gacha-premium chrome** (particle bursts on legendary+ pulls, portrait frame ornamentation, animated pull sequences) beyond the CSS glow above. The existing rarity color system (Phase 3) plus this pass's animations are a reasonable middle ground, not the full "AAA gacha" visual bar the brief describes.
- **Combat-scene sprite integration remains deferred** (see Phase 7 above) — the biggest visible gap between current state and the brief's full art vision.

## V1 status summary

Phases 1-6 are feature-complete and thoroughly unit-tested (82 Vitest tests across engine/loot/talents modules, all passing; clean typecheck/lint/build throughout). Phase 7's pipeline is real and working with a 12/13 sample batch integrated. Phase 8 got a light, honest pass rather than the full polish sweep, prioritized by the remaining session budget. The natural next steps for a future session: finish the sprite-integration risk properly (with room to test it thoroughly), run a real multi-playtest balance pass, and generate the rest of the 60-monster/relic roster's art now that the pipeline is proven.

## Follow-up session — GitHub Pages fix + real sprite rendering

- **GitHub Pages was serving a blank page because there was no build/deploy pipeline at all** — no `.github/workflows`, and Vite's default `base: '/'` assumes the site is served from a domain root, not a project-page subpath (`user.github.io/repo/`). Fixed with `base: './'` in `vite.config.ts` (relative references work at any subpath) plus a standard `actions/deploy-pages` workflow (`.github/workflows/deploy-pages.yml`) that builds and deploys `dist/` on push. Also switched the hardcoded `/game-assets/...` image paths (`RarityIcon.tsx`) from absolute-rooted to relative — same root cause, since this is a single-page app with no client-side routing, the current document URL is always the site root, so relative paths resolve correctly regardless of subpath. **One remaining manual step for the user:** GitHub repo Settings → Pages → Source must be set to "GitHub Actions" once (can't be done via git).
- **Finished the full asset generation pass**: all 16 monsters + the hero now have real Pollinations-generated art (previously only 4 monsters + hero). Hit the same rate-limit issue as before (429s) on a couple of items; the fix from last session (unconditional pacing between requests, not just after successes) held up — reran with `--only=<missing ids>` to fill exactly the gaps, which the resumable design made trivial.
- **`CombatScene` now renders real sprites instead of colored rectangles for the hero and every monster.** `preload()` loads a texture per monster id (`monster_<id>`) plus the hero (`hero_knight`); `createUnitView()` checks `this.textures.exists(key)` and uses a Phaser `Image` (`setDisplaySize` to the tier's box dimensions) when art exists, falling back to the original colored `Rectangle` otherwise — so any future monster added without art (or if generation partially fails) degrades gracefully instead of breaking. This required one structural change: the monster view is now destroyed and rebuilt fresh on every wave (`rebuildMonsterView()`, mirroring how ally views already worked) rather than mutated in place — Image and Rectangle don't share a resize/recolor API, and swap-by-rebuild sidesteps that entirely.
- **Companions still render as role-colored rectangles** — no companion art was generated this pass (budget call: hero/monsters are what's on screen during 100% of combat, companions are a bonus layer). Same fallback mechanism means adding companion sprites later is a pure data/asset addition, zero engine risk.
- **Background removal was skipped** — no `sharp`/`rembg` available in this environment and installing one would cost real setup time. Pollinations returns images on a near-white background, which reads acceptably as a "portrait card" behind each sprite rather than a glaring bug; real transparency is a clean follow-up once a lightweight image lib is available.

## Follow-up session — Relic↔companion synergy, Broken Blade, roster expansion, balance pass

**Scope:** close the Phase 4 gap flagged (and re-flagged through Phase 8) — companions fighting with flat, relic-blind stats — plus a flagship relic to prove it, 3 new companions, and a real balance-simulation harness.

### Decisions

- **`CombatEngine`'s damage pipeline is now genuinely party-wide, not hero-only.** `computeHeroDamage` was renamed `computeAttackDamage` and is now called from both `resolveHeroTurn` and the attack branch of `resolveAllyTurn` (tank/dps/summoner, not healer — no `healPercent` modifier kind exists, out of scope). `applyExecute`/`applyLifesteal` are called after any party member's hit, not just the hero's, and `applyReflect` now fires whenever the monster targets *any* living party member, not only the hero. The constructor parameter was renamed `heroModifiers` → `partyModifiers` to match — no signature change, same `AggregatedModifiers` object already threaded through `WaveManager`. This means all 60+ existing relics retroactively synergize with companions with zero changes to relic data — the fix was entirely in *consumption*, not in a new aggregation layer.
- **`attackSpeedMultiplier`/`maxHpBonusPercent` are baked into each companion's `attackIntervalMs`/`maxHp` in `WaveManager.buildAlliesAndSpells`**, mirroring exactly how the hero `Combatant` is built in `buildWaveEngine`/`tryPhoenixRevive`. Companion upgrade ranks (`COMPANION_RANK_BONUS_PER_LEVEL`) still only scale `attack`/`healAmount`, unchanged from Phase 5's HP-bookkeeping decision — relic-driven `maxHpBonusPercent` scales the same `def.maxHp` reference those ranks already treat as stable, so the two systems compose without conflict.
- **Broken Blade (legendary, `special: 'brokenBladeDamage'`) is the flagship relic proving out the new pipeline**, not a separate bolt-on mechanic — it's a plain `damageMultiplier` source computed in `WaveManager.computeModifiers()` from the run's live `state.brokenParts` total (1% per part, capped at 25 parts / +25%), following the exact same "computed from live state, not static aggregation" pattern `companionAuraSources` already established. Because it's `damageMultiplier`, it automatically benefits hero and companion attacks alike through the pipeline change above — no relic-specific companion code needed. It reads the *run's* Broken Parts count, not the meta-persisted currency that funds the Forge Weapon — the two systems share a name and a drop table (`rollBrokenParts`) but stay otherwise independent, same separation Phase 5 already drew between run gold and meta essence.
- **Companion roster grew 8 → 11**, filling role/rarity gaps rather than adding more of what already existed: `iron_vanguard` (rare tank — previously only one tank existed, at common), `hearthkeeper` (epic healer — previously only one healer existed, at rare), `warlords_aegis` (legendary support, aura `reflectDamagePercent` — previously legendary tier was dps-only and no companion aura used `reflectDamagePercent`). Registered the same id-driven way documented in `CLAUDE.md` — no gacha/loot/UI changes needed.
- **A real, committed balance-simulation harness now exists** (`src/engine/balanceSim.test.ts`) — the "100 seeded runs, naive always-pick-loot-option-0" simulation `CLAUDE.md` referenced was, on inspection, never actually committed in any prior session (confirmed via repo-wide search); it existed only as a prose result. Committed this time as a Vitest test with a `console.log` death-wave histogram plus a soft regression-guard assertion (`survivors >= 40/100` past wave 10), so future balance changes get an automatic floor instead of relying on someone remembering to re-run an ad hoc script.
- **No wave-scaling or Broken Blade constant changes were needed.** Running the new harness with the full pipeline change + Broken Blade + 3 new companions already in place landed at 49/100 survivors past wave 10 — within noise of the previously-documented ~50/100 baseline — despite companions now being a real, uncapped power increase (they benefit from every relic a run finds). Read as: the naive strategy rarely stacks enough companions + damage relics + Broken Blade simultaneously to swing the curve, so the existing `scaledMonsterStats` multipliers didn't need retuning this pass. Left as a candidate for a future session if real (non-naive) playtesting finds otherwise.

## Follow-up session — Abandon-run control, infinite-scaling wall, megaboss/ultraboss, sprite polish

**Scope:** a real playtest left a run running with no way to stop it. Root cause was two-fold: no UI control to leave a run while alive, and a purely linear wave-scaling curve with no mechanism that forces a strong build to eventually lose. Fixed both, added milestone boss tiers to punctuate very long runs, and did a targeted art/prompt pass.

### Decisions

- **`WaveManager.abandonRun()` reuses the existing `runOver` event/currency-deposit path instead of inventing a second "end the run" flow.** It just force-sets `isGameOver = true` and returns the same `{ type: 'runOver' }` event `tick()` already produces on death — `CombatScene`'s `depositCurrency`/`depositBrokenParts` handler for that event needed zero changes. A new `endReason: 'death' | 'abandoned'` field on `RunState` (mirrored in `runStore.ts`) is the only thing distinguishing the two, purely for `GameOverOverlay` copy ("Fell on wave X" vs "Retreated on wave X") — mechanically fleeing cashes out exactly like dying, which is the right idle-game default (you always keep what you earned).
- **The Flee button in `Hud.tsx` reaches into the running `CombatScene` (a Phaser scene, not React) via the same request-token pattern already established for loot choices** (`lootChoiceRequest`/`requestLootChoice`) — `abandonRunRequest`/`requestAbandonRun()` in `runStore.ts`, watched in `CombatScene.update()` exactly like the existing loot-choice check. No new cross-boundary mechanism was invented; this was purely "do the thing that already works for loot, for a second kind of player intent." Gated by a plain `window.confirm()` rather than new modal chrome — proportionate for a low-frequency, reversible-in-spirit (you keep your earnings) action.
- **The "must eventually end" requirement is solved by an era-compounding multiplier layered on top of the existing linear `scaledMonsterStats` curve, not by replacing the curve.** `ESCALATION_HP_MULT`/`ESCALATION_ATTACK_MULT` (1.12/1.08) compound once per 100-wave "era" (`era = floor(wave / 100)`), and are a complete no-op for waves 1-99 (era 0 → multiplier exactly 1) — the tuned early curve and the committed `balanceSim.test.ts` wave-10 regression floor are untouched by construction, verified by the sim still landing at 49/100 after this change. Hero power growth (level curve, capped Forge level, capped relic magnitudes like Broken Blade's 25% ceiling) is much closer to flat than compounding, so this guarantees the fight eventually becomes unwinnable — the actual mechanism that "lets overly long runs end," as opposed to the Flee button, which only lets the *player* end them voluntarily. Both were needed; neither alone solves what the other does.
- **Megaboss (every 100 waves) / ultraboss (every 1000 waves) are new `MonsterTier` values, not a re-skinned boss with a stat multiplier.** `tierForWave` checks them before boss/miniboss (ultraboss before megaboss, since 1000 is also a multiple of 100). TypeScript's exhaustive-`Record<MonsterTier,...>` checks caught every site that needed a case (`BROKEN_PART_DROP_TABLE`, `MONSTER_APPEARANCE`, the tier→monster-pool lookup in `WaveManager`) — the two non-type-checked sites (`Hud.tsx`'s `TIER_LABEL`/`TIER_COLOR`) were made `Record<MonsterTier, ...>` too specifically so this doesn't silently miss a future tier again. New content (`src/data/monsters/milestoneBosses.ts`): 2 megabosses (~600 hp base, picked randomly like any other tier pool) and 1 ultraboss (~2100 hp base, a singular "final wall" rather than a pool, matching how rare its appearance is). Their `xpReward`/Broken Parts drop table entries are deliberately generous (ultraboss: 15-25 parts guaranteed) as a milestone payoff, not just a punishment — an ultraboss kill alone nearly maxes Broken Blade's run-scaling cap.
- **Big-number formatting (`formatNumber` in `Hud.tsx`, e.g. `12.3k`/`1.2M`) was added preemptively for HP display**, since the escalation curve makes wave-500+ numbers genuinely large — this is a direct consequence of the scaling change, not a separate polish item, so it shipped in the same pass rather than waiting for someone to notice the HUD becoming unreadable.
- **Sprite polish stayed intentionally scoped to new content + a prompt/pipeline quality pass, not a full ~35-asset regeneration.** Pollinations' 25s-per-asset pacing makes a full regen a 15-20 minute unattended run with uneven, hard-to-verify-unattended results; instead: (1) tightened `CHIBI_STYLE`/`ILLUSTRATION_STYLE`/`PIXEL_ART_STYLE` in `generate.mjs` to lean explicitly into Brave Frontier's actual look (saturated anime-chibi proportions, bold line art, rim lighting) rather than generic "JRPG sprite" wording — this improves *any* future generation, not just this batch, regardless of which provider serves it; (2) generated real art for the only gap-filling content that had none: the 2 megabosses, 1 ultraboss, and the 3 companions added in the previous session (`iron_vanguard`/`hearthkeeper`/`warlords_aegis`).
- **A `&model=flux` param was tried on the Pollinations request to see if it'd improve quality, then reverted.** Testing (direct `curl` against the API, inspecting the JSON error body) showed Pollinations ignores the `model` query param entirely and always routes through its own internal "sana" backend regardless — the param had no verified effect, so it was removed rather than shipping a code comment claiming a benefit that couldn't be confirmed.
- **Pollinations then failed 9/9 on both generation attempts with HTTP 500 / `"Insufficient balance... PAYMENT_REQUIRED"`** — an anonymous-tier quota exhaustion on their end (confirmed via direct `curl`, reproducible across both a long styled prompt and a short generic one, so not prompt-content-dependent). Rather than wait it out, switched providers: `generate.mjs` already has AI Horde (a separate, free, anonymous community Stable Diffusion cluster) fully implemented as the *documented* primary provider — it just hadn't been used since Phase 7 because a prior session found Pollinations faster/more predictable and passed `--skip-horde` as the default workflow. Dropping that flag and re-running the same 9-asset batch succeeded 9/9 on AI Horde with zero code changes — confirming the two providers don't share a quota and that "switch provider" is a real, already-built fallback, not just a fallback in name. Slower (polling, up to ~90s/job vs. Pollinations' synchronous response) but that's a fine trade against a hard external blocker. `CLAUDE.md`'s pipeline section now documents this as the standard recovery move for a Pollinations outage, not a one-off workaround.

## Follow-up session — Per-class hero sprites, Kingdom essence sink

**Scope:** two requests — real distinct art per class instead of one shared portrait, and a new gold/essence sink for a maxed-out save. The user's first pitch for the sink used a "concubine collection" framing (conquer territories, bring back concubines); **declined** — collecting people as sexual conquest trophies isn't something to build regardless of art style, not a matter of wording. Reframed and confirmed with the user as territory conquest + recruiting allied lords/generals to the court, which delivers the same underlying gameplay need (an essence sink themed around kingdom-building) without that framing.

### Decisions

This flipped `tint`'s role: previously it was the *only* thing visually distinguishing classes (all four shared `hero_knight`); now real art does that job, so a color wash on top would just muddy it — all 4 classes' `tint` was set to `0xffffff`, which `createUnitView`'s existing `tint !== 0xffffff` check already treats as a no-op (that check predates this change; it wasn't added for it). `tint` stays in `ClassDefinition` purely as the fallback-rectangle color if a class's art is ever missing.

Fixed by decoupling: a new local `CLASS_ACCENT` map in `ClassSelect.tsx` (same file-local-lookup pattern already used there for `CLASS_ICON`) keeps the original per-class colors for the UI, while `ClassDefinition.tint` stays purely about sprite rendering. Two different concerns that happened to share one field before real art existed to need the split.
- **The Kingdom system reuses the exact `MetaBonuses`/`computeModifiers()` wiring already established for classes/Forge Weapon** (`kingdomModifiers: RelicModifier[]`, one more `ModifierSource` slot in `WaveManager.computeModifiers()`, resolved in `CombatScene.buildMetaBonuses()`) — no new pipeline concept, just one more contributor. `resolveKingdomModifiers()` in the new `src/engine/kingdom.ts` mirrors `resolveTalentModifiers` in `talents.ts` almost line-for-line.

Treasury reuses `costForRank` from `talents.ts` (same curve shape as every other ranked meta-progression), capped at level 50 rather than truly infinite — a hard cap was kept for consistency with every other ranked system in the game (Forge caps at 20, companion ranks at 5, Forge Weapon at its own max) rather than introducing the first-ever uncapped currency sink as a one-off exception.
- **`balanceSim.test.ts` needed no changes and shows no regression** — it runs with `DEFAULT_META_BONUSES`, which now includes `kingdomModifiers: []` by default, so a fresh-save naive-strategy run is completely unaffected by the new system, consistent with how the harness has never modeled Forge/talent meta-progression either.

## Follow-up session — Companion Ascension

**Scope:** feedback after Kingdom shipped, two complaints with one shared root cause: (1) once all 11 companions are unlocked, a Gacha duplicate pull refunds a little essence and does nothing else — no reason to keep pulling; (2) companions "feel almost useless," partly because `companionUpgrades` hard-caps at rank 5 (+8%/rank = 40% max), a low permanent ceiling. Ascension Shards (from duplicates) raising that cap fixes both at once.

### Decisions

- **Ascension raises the rank *cap*, reusing 100% of the existing rank-bonus combat math — zero `WaveManager`/`CombatEngine` changes.** `COMPANION_RANK_BONUS_PER_LEVEL` (+8%/rank, applied in `WaveManager.buildAlliesAndSpells`) already multiplies unboundedly by whatever rank a companion has; the old ceiling was purely `metaStore.upgradeCompanion`'s check against the fixed `MAX_COMPANION_UPGRADE_RANK` constant. `companionMaxRank(ascensionLevel) = MAX_COMPANION_UPGRADE_RANK + ascensionLevel` replaces that fixed check — the smallest possible change that unlocks real long-term growth, deliberately not a base-stat rebalance (a separate, riskier question — see `CLAUDE.md`'s Known gaps).
- **Ascension spends a new, separate currency (shards) rather than essence.** Essence already has four sinks (Talents/Forge/Companion ranks/Kingdom); routing Ascension through essence too would've just been "one more thing essence buys," not a genuine answer to "duplicates need their own purpose." Shards only come from duplicate pulls of that specific companion, so the loop is self-contained: pull → (maybe) duplicate → shard → ascend → higher rank cap → pull more to fund the next rank.
- **Shard yield scales with rarity (1/2/3/5/8 for common→mythic)** rather than a flat 1-per-duplicate — a mythic Astral Seraph duplicate (a genuinely rare, expensive-feeling pull) is worth 8x a common Roguish Blade duplicate, so high pulls stay exciting even as "just a duplicate" instead of feeling equally deflating regardless of rarity.
- **`ascensionShardCost` reuses `costForRank` from `talents.ts`** (same curve shape as every other ranked system: Talents/Forge/Companion ranks/Kingdom Treasury) rather than inventing a new cost formula — consistent with the codebase's established "one growth-curve function, many currencies" pattern.
- **`MAX_ASCENSION_LEVEL = 20` (effective max rank 25, up to 200% bonus)** — finite, not literally infinite, matching every other system's choice to cap at a large-but-bounded number (Forge 20, Kingdom Treasury 50) rather than make Ascension the one true exception. Still a 5x jump over the old ceiling, which is the actual point.
- **No new store test file** — consistent with the project's established boundary that Vitest covers engine logic only (`CLAUDE.md`'s Stack line); `conquerTerritory`/`upgradeTreasury` and now `ascendCompanion` all follow the same afford-and-spend pattern and were verified via `npm run dev` smoke testing rather than unit tests, matching how every other `metaStore` action has been handled.
- **Deliberately did not touch companion base stats or attempt a broader "content feels thin" fix in this pass.** Both were raised in the same feedback round but are separate, larger questions (a real balance pass needs simulation or playtesting; a long-term progression goal beyond repeating existing systems is closer to a prestige/rebirth design than a quick fix) — flagged as open items in `CLAUDE.md` rather than folded into a change that was meant to stay small and low-risk.

## Follow-up session — Gacha pity

**Scope:** implement the pity system flagged as a known gap since Phase 8 (`CLAUDE.md` item 7) — a bad unlucky streak on an 11-character pool previously had no floor at all, pure independent rolls forever.

### Decisions

- **Both `pullGacha`/`pullGachaMulti` kept their exact old signature and return shape — pity is an optional trailing parameter that defaults to a fresh streak.** With the param omitted, a single call's pity state starts at `{0,0}` every time, which can never cross either threshold (10/50) within one call, so behavior is provably identical to the pre-pity implementation for any caller that doesn't pass it. This meant **zero changes to the 10 pre-existing `gacha.test.ts` cases** — new pity tests were purely additive.
- **Pity resets are keyed off the *actually received* rarity (`result.companion.rarity`), not the rarity the roll targeted.** `rollGachaRarity` can force a "rare+" or "legendary+" target, but the existing empty-pool fallback (`pool.length === 0 → pool = candidates`) can still hand back a lower-rarity companion if the pool genuinely has none of the forced tier. `nextPityState(pity, rarity)` is a separate pure function that folds in whatever rarity the player actually got, so a fallback case correctly does *not* silently reset the counter and skip the guarantee.
- **`weightedPick(rng, rarities)` replaces the old inline cumulative-weight loop, generalized to roll over an arbitrary subset of rarities** (full table normally, rare+ only or legendary+ only when pity forces) rather than writing three near-duplicate rarity-rolling functions. Renormalizes by summing only the candidate subset's weights, so e.g. a forced rare+ roll still respects the *relative* rare:epic:legendary:mythic odds from `GACHA_RARITY_WEIGHTS`, just with `common` excluded — no separate "pity odds" table to keep in sync with the main one.
- **`pullGachaMulti` threads pity through its internal loop** (each of the 10 pulls in a batch can itself trigger or reset the streak) but still returns a plain `GachaPullResult[]`, same as before — `metaStore.ts` derives the final pity state itself by folding `nextPityState` over the returned array (`results.reduce(...)`), reusing the same exported pure function rather than having `pullGachaMulti` also return pity out-of-band. Keeps the engine function's contract simple (array in, array out) while still letting the caller reconstruct exact state.
- **Thresholds (rare+ at 10, legendary+ at 50) are safety nets, not a primary income path** — expected pulls-to-rare+ under the existing weights is ~2, and expected pulls-to-legendary+ is ~17, so both floors trigger rarely by design; they exist purely to cap the tail-risk of a bad streak, not to change the game's expected pull economy.
- **`GachaTab` shows the live streak** (`X/10 to guaranteed rare+ · Y/50 to guaranteed legendary+`) so a run of bad luck reads as visible progress toward a guarantee instead of just feeling unlucky — standard gacha-genre UX, cheap to add since `gachaPity` was already a plain persisted field.

## Follow-up session — Kingdom art, zone backdrops, attack-frame sprites

**Scope:** three content/polish requests together — Kingdom territories/lords had no art (plain text rows), zones only differed by a flat background color, and combat was still single-portrait/tween-only. The user explicitly picked the highest-risk option for the third ("full sprite-sheets on the whole roster") despite being warned that independent txt2img generations don't stay visually consistent frame-to-frame — see the img2img investigation below for how that risk actually played out.

### Decisions

- **Kingdom/zone art landed exactly like every other content category** — new `landscape` style in `generate.mjs` (painted environment/banner art, distinct from the existing `illustration`/`pixelArt` character styles), no background removal for territories/zones (they're full-bleed scenes, not cutout subjects, unlike every previous category), `removeBackground.mjs lords` reuses the existing character-portrait treatment. Zero new architecture — this is squarely "add manifest entries, run the pipeline, wire `GeneratedPortrait`," the same pattern used for every prior art batch.
- **Zone backdrop rendering keeps the solid-color fallback as the permanent floor, not a one-time migration.** `applyZoneBackground()` always sets `cameras.main.setBackgroundColor()` first, then layers a full-canvas `Image` + dark scrim on top only if that zone's texture is loaded — so a zone with missing/failed art degrades to exactly today's flat-color behavior instead of a blank/broken screen. Same `textures.exists()`-gated pattern as hero/monster/companion sprites, just applied to a fourth asset category.
- **The scoped attack-frame deliverable was explicitly 2 frames per unit (idle + attack), not a true multi-frame sheet** — stated up front in the plan before any generation ran, because 100+ generations (idle/attack/hurt/death × 34 units) at up to ~90s/job on AI Horde wasn't viable in one session. This was the honest ceiling on "full roster," not a silent downscope.
- **img2img was the planned fix for frame-to-frame consistency, and it didn't work — discovered empirically, not assumed.** The plan called for generating each attack frame *from* its idle portrait via AI Horde's `source_image`/`source_processing: 'img2img'`, anchoring the new pose to the same character/colors. Tested at `denoising_strength` 0.55 (near-identical to source), 0.8 (still near-identical), and 0.95 (still near-identical) on the same test subject (Knight) — the anonymous AI Horde tier does not appear to honor the parameter at all; every value produced what was essentially a copy of the source composition regardless of how much freedom was requested. A direct plain-txt2img comparison on the same prompt produced a genuinely different, dynamic pose (confirming img2img was the broken variable, not the prompt or the pose-fragment wording).
- **Reverted to plain txt2img for attack frames rather than keep debugging AI Horde's img2img internals blind.** Diminishing returns on further probing (source_image format, alternate param names, etc.) against a community/anonymous backend that's already documented elsewhere in this file as flaky. txt2img reliably delivers what actually matters for this feature — a visibly different pose during the attack lunge — at the cost of "close, not exact" character consistency between a unit's two frames. That's the same tradeoff already shipped and accepted for companions' two independently-generated illustration/pixelArt art styles, so it's not a new category of risk for this codebase, just the same one applied to a new asset pair.
- **`CombatScene` wiring needed no engine changes** — `attackLunge()` already ran a lunge-out/lunge-back tween pair for every attack; `swapUnitFrame()` just hooks the texture swap to the start of the lunge-out and the completion of the lunge-back, reusing a factored-out `applyContainFit()` (previously inline in `createUnitView`) since an attack-frame image can have different native dimensions than its idle sibling. Units with no attack frame (or a rectangle-fallback body) are unaffected — `swapUnitFrame()` no-ops if the texture isn't loaded or the body isn't a Phaser `Image`.
- **`manifest.mjs`'s `attackFrameManifest` is derived, not hand-written** — `manifest.filter(hero/monsters/companions).map(frame: 'attack')` — so every future roster addition automatically gets an attack-frame manifest entry with zero extra authoring, the same "derive from the existing list" instinct already used elsewhere (e.g. `allZones` sorted from a registry) rather than a second hand-maintained list that could drift.
- **The last 2 stragglers (`iron_vanguard`, `roguish_blade`) both eventually succeeded on a later retry, closing the roster to 34/34.** `iron_vanguard_attack` had failed AI Horde 3 times to what looked like a provider outage; a subsequent retry succeeded via the Pollinations fallback with no code changes. `roguish_blade_attack`'s one successful generation had been blocked by AI Horde's own safety classifier (flagged as potential CSAM, near-certainly a false positive on a completely benign "hooded rogue with daggers" prompt) — the flagged file was deleted immediately and not retried in that moment; a later attempt with the identical prompt generated cleanly via Pollinations instead, with no recurrence of the flag.
